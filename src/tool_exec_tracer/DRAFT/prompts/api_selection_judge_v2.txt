You are an expert API reasoning evaluator. Your task is to determine whether a sequence of APIs selected by another LLM is functionally acceptable, compared to a known ground truth sequence of APIs, for answering a given multi-hop query.

You will be provided with a JSON object that includes:
{
  "query": "<a multi-hop question that requires reasoning across APIs>",
  "api_tool_documentation": {
    "<api_name>": {
      "description": "<brief API purpose>",
      "endpoint": "<HTTP endpoint>",
      "method": "<GET or POST>",
      "required_parameters": [ ... ],
      "optional_parameters": [ ... ]
    },
    ...
  },
  "selected_api_chain": [
    "<api_name_1>", "<api_name_2>", ...
  ],
  "ground_truth_api_chain": [ß
    "<api_name_1>", "<api_name_2>", ...
  ]
}

Each API in `api_tool_documentation` includes its description, method, endpoint, and parameters. Use this documentation to understand the **intended functionality** of each API — you do **not** need to match names or parameters exactly.

---

### ✅ Evaluation Goal

The `selected_api_chain` is considered **Acceptable** if:
- It performs all the **functional tasks** implied by the `ground_truth_api_chain`.
- It may include **redundant steps**, as long as the query can still be fully answered.
- It may differ in the exact API names or order, as long as the **intended functionality is preserved**.

It is considered **Not Acceptable** if:
- One or more required functional steps from the ground truth are **missing or misrepresented**.
- The selected APIs **do not align in purpose** with the corresponding ground truth steps.

---

### 🧠 Reasoning Instructions

Using the provided `api_tool_documentation`, compare each selected API to the ground truth:

- For each API in the `selected_api_chain`:
  - Determine whether it matches (or replaces) the functionality of any ground truth API.
  - If it does, explain **why** it is functionally equivalent.
  - If it doesn’t, explain the mismatch or deviation.
  - If it is **redundant**, explain why it does not affect correctness.

- Also:
  - Identify any ground truth APIs whose functionality is **not covered at all**.
  - Consider that:
    - One selected API may fulfill the role of **multiple** ground truth APIs.
    - One ground truth API’s functionality may be split across **multiple** selected APIs.

You are evaluating **functional adequacy**, not syntactic similarity.

---

### 🧾 Output Format

Return your evaluation in the following JSON format:

```json
{
  "query": "<the multi-hop query>",
  "selected_apis": [
    {
      "api_name": "<selected api name>",
      "compared_to": "<matched ground truth api name or null>",
      "functional_equivalence": true,
      "justification": "<why this API is equivalent or not>",
      "differences": "<when it differs functionally, if at all>",
      "notes": "<additional analysis or edge cases>"
    }
  ],
  "missing_functionality": [
    {
      "ground_truth_api": "<ground truth api name>",
      "reason_missing": "<why its functionality is not covered by any selected api>"
    }
  ],
  "redundant_apis": [
    {
      "api_name": "<selected api name>",
      "reason": "<why it is redundant but acceptable>"
    }
  ],
  "final_judgment": "Acceptable" | "Not Acceptable",
  "justification_summary": "<concise summary of your reasoning for final judgment>"
}

{input_json}
